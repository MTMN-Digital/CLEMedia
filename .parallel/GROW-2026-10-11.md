# Growing the drawings for the graphite, 2026-10-11

Read this with `.parallel/HAND-2026-10-11.md`, which is still in force. This
is an addition to it, not a replacement.

## What happened and what you are being asked to do

The drawings got a wobble on 2026-10-11 and the client's verdict was:

> "drawing animations are very very nice, but they feel a tiny bit off,
> because they are solid lines that are trying to look handdrawn. i think the
> solution is making the drawings larger so then we can apply like a pencil
> texture to the strokes."

He is right about the cause and right about the fix. A solid shape with a
bent outline is still a solid shape; what makes a pencil line read as pencil
is that the graphite misses the troughs in the paper, so the line is eaten
away along its edge.

**That tooth is already built and frozen.** `components/draw/InkDefs.tsx` now
carries a second noise, turned into an alpha mask and composited into the
stroke. It was tuned against four settings photographed side by side. You do
not change it, and you do not add a filter of your own.

## THE ONE NUMBER THAT MATTERS

**A stroke needs about four device pixels for the tooth to read.** Below that
there is no room inside the line for a grain cell and the result is noise
rather than graphite. Measured: at a 256px render of a 240 unit drawing the
tooth is dirt; at 512px it starts working; at 768px it is clearly pencil.

Every drawing on this site is currently authored at roughly **one user unit
per CSS pixel**, which puts a 2 unit `.ink-line` at about 2 device pixels.
That is half what the tooth needs. **This is the whole job.**

So, for the drawing you own, work out its real ratio:

```
px per unit = (the CSS width the drawing actually renders at) / (its viewBox width)
```

Measure it, do not guess it: the CSS width is whatever the container gives it
at 1440, which is often capped by a `max-width` in the drawing's own
stylesheet. Then get `px per unit` to **at least 2.0**, by either:

1. **Giving the drawing more room on the page.** Preferred where the page can
   spare it. A drawing that was a thumbnail beside a paragraph becomes a
   drawing.
2. **Re-authoring its coordinates smaller** against the same rendered width,
   if the page genuinely cannot give it more room. Halving every number in a
   240 unit drawing and setting `viewBox="0 0 120 95"` gets the same result
   with no layout change at all. Stroke widths come from the kit and do NOT
   get halved: that is the point, the stroke keeps its device size while the
   drawing's own geometry gets finer around it.

**And if neither is possible, say so and use `.ink--fine`.** That is a second
filter, already built, that keeps the wobble and drops the tooth. It exists
for drawings whose size is set by something other than the drawing: a float
bounded by the prose measure, a mark inside a card. Using it is a legitimate
answer and is much better than shipping a 2px stroke full of noise. What is
NOT acceptable is leaving a small drawing on the default filter.

## Do not add a mobile fallback, it is already answered

Shooting a full width drawing at 390 shows the tooth as noise, and the
obvious conclusion is that small screens need `.ink--fine` behind a media
query. They do not. That screenshot was taken at a device pixel ratio of 1;
real phones are 2 or 3, the filter rasterises at DEVICE resolution, and
re-shot at `deviceScaleFactor: 3` the tooth is clean. Measured on
2026-10-11. Do not add a breakpoint rule, and if you think you have found a
case, measure it in device pixels first and report it rather than patching
it locally.

## What you may not do while growing a drawing

- **No copy is cut to make room.** Standing instruction from the client, and
  it has been reaffirmed twice. If a drawing cannot grow without taking space
  from the client's words, it does not grow: re-author its coordinates, or
  take `.ink--fine`.
- **Do not break the reading.** Several of these drawings were redrawn hours
  ago to fix exactly that. Grow the drawing, do not redesign it. If growing it
  genuinely exposes a composition problem, fix that too, but say so.
- **Mobile first.** A drawing that doubles on a desktop must still work at
  390. Check it.
- Contrast, reduced motion, `pathLength="1"`, one accent, no em dashes: all
  as in the hand contract.

## How to check

Do NOT run `npm run build`; several workers are running at once. Run
`npx tsc --noEmit -p tsconfig.app.json`.

Start your own dev server on a port nobody else is using and shoot your
drawing with `node scripts/qa/shot.mjs <url> <selector> <out.png> 1440`, then
**read the PNG at 2x or 3x**. The difference between graphite and dirt is not
visible at 1x in a page screenshot and is obvious the moment you zoom. Shoot
at 390 as well. Kill your server when you are done.

Report the before and after `px per unit` for every drawing you own, as a
number, and say which of the three routes you took for each.
